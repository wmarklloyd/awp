# Agent Workshare Protocol design

AWP 0.6.0 is the stable exploratory release. AWP 0.8.0 is an unreleased working draft that introduces explicit governing-specification binding with new family, module, and discovery-schema versions.

The protocol preserves portable semantic work state for human and agent continuation. It separates intent, authority, execution, evidence, and conclusion; distinguishes reported, inferred, observed, verified, disputed, stale, and refuted claims; and treats event ancestry as causal truth while snapshots and Markdown remain projections.

The preferred exchange representation is a human-readable `<project-name>.awp.md` capsule. This project demonstrates that convention through `awp.awp.md`. Coordination defines deterministic lifecycle candidates, semantic scopes, bounded negotiation, explicit user-mediated arbitration for unresolved agent interactions, contracts, typed preconditions, verification binding, staleness propagation, integration semantics, and optional fenced live enforcement.

Complete bundled specification: [AWP 0.6.0 specification bundle](https://raw.githubusercontent.com/wmarklloyd/awp/v0.6.0/AWP_SPECIFICATION_0.6.0.bundle.md).

The project’s four target use cases are maintained in [the project scope](docs/project-scope.md): durable semantic descriptions, clear shared orientation, recorded checkpoint resumption, and coordination of interdependent changes above source control.

Current status: released and draft materials are separated and immutable release identifiers remain preserved. Cooperation Contracts 0.1 is a registered experimental module: COOP-0 supports uncoordinated but substantive collaboration, COOP-1 specifies small-group guarded work and bounded symbiotic interactions, and COOP-2 is reserved for a future stronger envelope. Two bounded Codex/Claude interactions used shared stores from different execution paths, compatible concurrent scopes, and receipt-backed exits. The adapter now reports a schema-valid binding disclosure, checks canonical capsule integrity before guarded work, records shared-reach handshake evidence, and can publish a receipt-backed checkpoint with separate capsule and ledger stale-writer checks. This is useful component evidence, not a complete COOP-1 conformance claim.

Recommended next action: implement binding-owned interaction storage, canonical repeat-key computation, deduplication, and loop-budget enforcement; then exercise fresh entry from a newly projected canonical capsule. Preserve the separate Coordination C0–C3 conformance axis.

Planning update: [Cooperation Contracts 0.1](spec/drafts/0.8.0/cooperation-contracts.md) defines COOP-0, COOP-1, and future COOP-2 as a separate experimental profile family. COOP-1 combines declared guarded-scope blocking with bounded, decision-owned feedback loops for review, critique, alternatives, delegation, decision support, and synthesis. Its policy accepts extension parameters and requires unknown required parameters to be enforced by a compatible binding, delegated, or declined. This profile does not rename or replace Coordination C0–C3, and current tools do not yet establish complete COOP-1 conformance.

Planning update: the user requested an architecture that smaller models can implement. See [Model participation architecture and implementation plan](docs/model-participation-architecture.md). This informative proposal defines five model operations, delegated processing responsibilities, bounded context, receipt-based publication, freshness, and recoverable checkpoint/exit behavior. The responsibility matrix in [docs/model-participation-matrix.md](docs/model-participation-matrix.md) now assigns each operation and C1 behavior to its owning component. Operation state machines are documented in [docs/model-participation-state-machines.md](docs/model-participation-state-machines.md), and ten worked conversations are documented in [docs/model-participation-conversations.md](docs/model-participation-conversations.md). The local adapter now has a limited `checkpoint` continue path: it records a durable receipt only when a supplied capsule frontier matches the ledger frontier, and keeps exit pending until terminal intent, capsule projection, and presence-release bindings are implemented. The architecture is proposed; it does not establish new C1 conformance or change the governing capsule version. The generated checkpoint below records the current contract-design milestone.

Planning update: the experimental participation schema and three structural examples are now present. They define the five model-facing request operations, a common operation response, and a publication receipt. The local adapter now implements read, announce, and publish; its request-id table makes retries durable within the same workstate ledger, while interact, checkpoint, host authority, and complete C1 composition remain outstanding.
